# ADR-003: Groth16/BN254 as ZK-SNARK Proof Scheme

**Status:** Accepted

---

## Context

The system must prove to a public blockchain that an investor's accumulated ROI is correct, without revealing the individual transaction details (symbols, amounts, timing) that constitute their competitive advantage. This requires a Zero-Knowledge proof scheme.

The main candidates evaluated were:

| Scheme | Proof Size | Verification Cost | Trusted Setup | Recursive |
|---|---|---|---|---|
| **Groth16/BN254** | ~256 bytes | ~200K gas | Yes (per-circuit) | No (natively) |
| PLONK/BN254 | ~768 bytes | ~300K gas | Universal | Yes |
| STARKs | ~50–200 KB | ~1M+ gas | None | Yes |

---

## Decision

Use **Groth16 over the BN254 (alt-bn128) elliptic curve**, implemented with **Circom 2.1.6** (circuit compiler) and **SnarkJS** (proof generation and verification).

Additionally, use **Poseidon hash** and **EdDSA over BabyJubJub** as the cryptographic primitives throughout the system, because both are natively supported as in-circuit components in Circom, eliminating the need for expensive SHA-256/ECDSA adapter circuits.

---

## Consequences

**Positive:**
- **Smallest proof size**: Every Groth16/BN254 proof is exactly 3 elliptic curve points — ~805 bytes as calldata. This is constant regardless of circuit complexity.
- **Constant verification time on-chain**: The EVM `ecPairing` precompile makes verification cost fixed and predictable (~363K gas for the full `BatchTxVerifier`).
- **Native tooling**: The EVM has precompiles for BN254 operations (`ecAdd`, `ecMul`, `ecPairing`), allowing Solidity verifiers generated by SnarkJS to work without any custom precompile.
- **Poseidon/BabyJubJub alignment**: Using these primitives for receipt signing means the same cryptographic operations used at trade time are also verified inside the circuit, with no adapters needed.

**Negative / Trade-offs:**
- **Trusted setup required**: Groth16 requires a circuit-specific trusted setup ceremony (`Powers of Tau` + circuit-specific Phase 2). The prototype used a single-participant setup. A production deployment would require a public multi-party ceremony (see Future Work).
- **No native recursion**: Groth16 does not natively support incremental proving. Batch size is fixed at compile time (N=5 in the current circuit). Recursive techniques (Nova/SuperNova) are identified as future work.
- **ZK proving time**: Generating a Groth16 proof for the `BatchTxVerifier` circuit takes ~14.5 seconds median on a 2.8 GHz Intel i7 (CPU-only). This is acceptable because proof generation is asynchronous — it does not block the user's trade execution.
